Memory as a 2D array: depth × width

Every memory chip, no matter the technology inside, presents the same simple shape to the outside world: a rectangular array of bit cells, addressed by row.

Depththe number of rows = the number of separately-addressable "words". If there are N address bits, depth = 2N.
Widththe number of columns = the number of bits in each word (how many data lines the chip exposes at once, M).
Array sizedepth × width = 2N × M total bit cells.
Address lines needed = log₂(depth)    Data lines needed = width
Analogy Think of a memory chip as a wall of PO boxes: the address is the box number you dial in (how many digits you need depends on how many boxes there are), and the data width is how many letters fit in each box at once. More boxes needs more address digits; bigger boxes needs more data lines — these are two completely independent design choices.

ROM vs. RAM: the fundamental split

ROM (Read-Only Memory)non-volatile (keeps its data with the power off); fast to read, but writing is slow, difficult, or (for true ROM) impossible after manufacture. Used for boot code and firmware — things that must survive a power cycle.
RAM (Random Access Memory)volatile (loses everything the instant power is cut); fast to both read and write. "Random access" just means any address costs the same time to reach — unlike, say, magnetic tape, where reaching a far-away address means physically winding through everything in between.

Implementing logic directly with a ROM

Any Boolean function of n inputs can be implemented by simply storing its entire truth table in a ROM: n inputs feed an n-to-2n decoder, each decoder output becomes one "wordline" (activating exactly one row), and each bitline reads out whatever bit was stored in that row/column intersection. This is conceptually the same "look up the answer in a giant pre-computed table" idea as a PLA/PAL (Week 6) — a ROM is really just a decoder plus a fixed, one-time-programmed OR-plane.

Addressing a memory: why square arrays are preferred

A naive design would use one giant N-to-2N decoder to pick a single row directly — but for a large memory, that decoder becomes absurdly large (the lecture's example: a plain 1M×1 RAM addressed this way would need over a million 20-input NAND gates). The standard fix is two-dimensional decoding: arrange the array as close to square as possible, split the address into a row-address part (feeding a row decoder) and a column-address part (feeding a much smaller multiplexer that picks the right column(s) out of the selected row). This keeps every decoder small, and keeps the physical wiring (data/address lines) short.

n + m address bits → 2n rows × 2m columns per row, with a 2m:1 multiplexer selecting the final k-bit word

ROM timing: access time, chip-select, output-enable

tAAaccess time from the address becoming stable — how long until valid data appears, assuming the chip is already selected and enabled.
tACSaccess time from chip-select — relevant when the address was ready first and chip-select arrives later.
tOE / tOZhow long after Output-Enable is asserted until data appears (tOE), and how long after it's de-asserted until the output goes back to high-impedance (tOZ).

SRAM: memory built from ordinary flip-flops

An SRAM cell is literally a small cross-coupled latch (Week 8) plus access transistors gating it onto a pair of bitlines — which is exactly why it's called static: as long as power stays on, it holds its value indefinitely with no extra effort, the same as any flip-flop. The cost of that convenience: an SRAM cell typically needs 6 transistors, making it markedly less dense (more silicon area per bit) than DRAM.

Write operation requirements mirror the setup/hold discipline from Week 11 almost exactly: the address must be stable before writing begins, and the data must be stable before the write ends — get either wrong, and you risk writing to the wrong cell, or writing the wrong value.

DRAM: one transistor, one capacitor, per bit

A DRAM cell stores its bit as charge on a tiny capacitor — a logic 1 is "capacitor charged", a logic 0 is "capacitor discharged". This needs only one transistor per cell (versus SRAM's six), making DRAM far denser and cheaper per bit — at the cost of being dynamic: that stored charge slowly leaks away, so every cell must be actively "refreshed" (read and rewritten) periodically, typically every 4–64ms, or the data is lost.

Reading a DRAM cell is destructive: the tiny stored charge is too small to read directly, so the bitline is first pre-charged to VDD/2, the wordline is raised, and the cell's capacitor shares its charge with the bitline, nudging its voltage very slightly up or down from VDD/2 — a sense amplifier detects that tiny nudge and amplifies it back up to a clean logic level. But sharing that charge with the bitline drains the capacitor in the process — so after every single read, the cell's original value must be explicitly written back, or it's lost for good.

Analogy An SRAM cell is like a light switch — it stays in whatever position you left it, indefinitely, using no extra effort. A DRAM cell is like a leaky bucket holding a little water: it slowly drains no matter what, so someone has to keep going around and topping every single bucket back up (refreshing it) — but building a million tiny leaky buckets is much cheaper and smaller than a million light switches.

DRAM address multiplexing: RAS and CAS

To keep the pin count down, DRAMs split their address into a row address and a column address and send them over the same physical address pins, one after another, distinguished by two control signals:

RAS̄ (Row Address Strobe)tells the chip "the bits on the address pins right now are the row address" — loads them into the row latch and reads out that entire row internally.
CAS̄ (Column Address Strobe)tells the chip "the bits on the address pins right now are the column address" — selects which bit(s) of that already-read row actually reach the data pins.

This is exactly why a DRAM with 2N total address bits only needs N physical address pins — the same trick as the "2D decoding" idea above, taken one step further by reusing the same physical pins twice per access instead of just splitting the decoder logic.

DRAM refresh: the formulas that matter

Number of refresh cycles required = number of rows in the array
Refresh cycle interval = Refresh interval (data retention time) ÷ Number of refresh cycles
Refresh overhead (%) = (actual refresh time used) ÷ (refresh interval) × 100%

One refresh cycle refreshes an entire row at once (since reading any bit in a row already reads — and therefore requires rewriting — the whole row), which is precisely why the number of required refresh cycles equals the number of rows, not the number of individual cells.

Q3
Tests: address lines = log₂(depth), data lines = width

How many address lines and data lines are needed for: (a) 16K×8 (b) 256K×64 (c) 2G×16 (d) 20×4 (e) 16 Mbytes?

Answer (computed directly)
ModuleAddress linesData lines
16K × 814 (log₂16384=14)8
256K × 6418 (log₂262144=18)64
2G × 1631 (2G=2×2³⁰=2³¹)16
20 × 45 (2⁴=16<20≤32=2⁵, so 5 lines, with some addresses unused)4
16 Mbytes24 (16M=2²⁴, assuming byte-wide/×8 organisation)8

The one to be careful with is (d): 20 is not a power of 2, so you need enough address lines to reach at least 20 distinct codes — 4 lines only reach 16, so you need 5 (reaching 32, with 12 addresses left unused). Case (e) needed one assumption spelled out explicitly: "16 Mbytes" alone doesn't tell you the width, so I assumed the standard byte-addressable (×8) organisation to get a concrete depth of 2M words.

Q4
Tests: total cell count vs. address lines, and the square-array addressing layout

For an 8 Kbytes SRAM: total number of cells? Address lines required? Show a possible square-array physical layout.

Answer (computed directly)

Total cells: 8 Kbytes × 8 bits/byte = 65,536 individual 1-bit SRAM cells (this counts every physical storage cell, regardless of how the external interface is organised).

Address lines: treating it as 8K individually-addressable bytes (8-bit words), depth = 8192 = 213 → 13 address lines (with 8 data lines for the byte-wide output).

Square physical layout: 65,536 = 256 × 256 exactly (I confirmed this by computing √65536 = 256 directly) — so a natural physical layout is a 256-row × 256-column cell array. An 8-bit row decoder (28=256) selects one of the 256 rows; each 256-bit row then holds 256÷8 = 32 separate 8-bit words, so a 5-bit column address (25=32) drives a 32:1 multiplexer per data bit to pick out the right byte. Check: 8 row-address bits + 5 column-address bits = 13 total address bits — exactly matching the 13 address lines computed above, confirming the layout is self-consistent.

Q5
Tests: the full DRAM refresh-overhead calculation, end to end

A Hitachi 256Mbit DRAM, refreshed every 64ms: (a) address input pins? (b) row/column configuration? (c) refresh cycles for the whole chip? (d) refresh period per cell? (e) if refresh time is 35ns, how many refresh cycles fit in one refresh period? (f) what percentage of time is spent refreshing?

Answer (computed and cross-checked)

(a) Address pins: 256Mbit = 228 total bits, needing 28 address bits for a full linear address — but since DRAM multiplexes row and column addresses onto the same physical pins (RAS/CAS, Slides section), and a square array needs equal row/column address widths (28÷2=14 each), only 14 physical address input pins are needed.

(b) Row/column configuration: √(228) = 214 = 16,384 rows × 16,384 columns (a genuinely square array, confirmed by direct computation).

(c) Refresh cycles for the whole chip: one refresh cycle refreshes one full row (Slides section), so this is simply the number of rows: 16,384 refresh cycles.

(d) Refresh period per cell: this is just the given retention/refresh interval spec restated: every individual cell must be refreshed at least once every 64ms.

(e) Refresh cycles that fit in one 64ms period, at 35ns each: 64ms ÷ 35ns = 64,000,000ns ÷ 35ns ≈ 1,828,571 cycles — this is the theoretical capacity available in that time window, deliberately much larger than the 16,384 actually required (that gap is exactly why refresh overhead, part f, ends up so small).

(f) Percentage of time spent refreshing: actual refresh time used = 16,384 cycles × 35ns = 573,440ns; total available window = 64ms = 64,000,000ns. 573,440 ÷ 64,000,000 × 100% ≈ 0.90% — I computed this via a small script rather than by hand to avoid a unit-conversion slip between ms and ns, given how easy that particular mistake is to make.

✍️ Write This Down

Copy these into your own notes:

  • Memory shape: depth (rows, = 2^address-lines) × width (columns, = data lines). Array size = depth × width.
  • ROM: non-volatile, fast read, slow/impossible write. RAM: volatile, fast read AND write.
  • Two-dimensional decoding: split the address into row (large decoder) + column (small multiplexer) to keep a large memory's decoding logic and wiring manageable — always aim for a roughly square array.
  • SRAM: a latch/flip-flop per bit (6 transistors), holds data with no refresh needed, but low density. DRAM: a capacitor per bit (1 transistor), needs periodic refresh (leaks charge), but very high density.
  • Reading a DRAM cell is destructive — the read must always be followed by a write-back of the original value.
  • RAS (Row Address Strobe) and CAS (Column Address Strobe) let a DRAM reuse the same address pins twice per access (row, then column) — halving the pin count needed.
  • Refresh formulas: refresh cycles needed = number of rows; refresh cycle interval = refresh interval ÷ number of rows; refresh overhead % = (refresh cycles × time per cycle) ÷ refresh interval × 100%.

🟥 Redstone Build: A Tiny Addressable Memory

Redstone can't easily model a leaking capacitor, so a literal DRAM cell isn't a natural fit — but the addressing/decoding structure that sits around any memory array (ROM, SRAM, or DRAM alike) translates perfectly.

  1. Build a 2-to-4 decoder (Week 6) feeding 4 separate "wordlines".
  2. Behind each wordline, wire up a small row of 4 hard-wired lever/torch combinations (some ON, some OFF) representing 4 permanently "stored" bits — this is literally a small ROM: the decoder picks exactly one wordline, and that wordline's fixed pattern of torches drives 4 shared "bitline" lamps.
  3. Confirm: as you change the 2-bit address input, exactly one of the 4 stored 4-bit patterns appears on the 4 output lamps at a time — a working, physical 4-word × 4-bit ROM, built from the exact same decoder-plus-stored-pattern structure as the lecture's "logic implementation with ROM" example.
  4. Stretch goal — make it writable (a tiny SRAM): replace each hard-wired torch pattern with one of your Week 8 D-latch cells instead, and gate each latch's clock input with its own wordline (so only the addressed row's latches actually update when you write). You now have a genuine 4-word × 4-bit read/write memory: pick an address, write a pattern, pick a different address, write a different pattern, then return to the first address and confirm it still remembers what you originally stored.
