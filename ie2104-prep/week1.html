Concept 1 of 3

Why does this topic even exist?

A digital circuit is really just a huge network of switches. A switch has exactly two stable states — off or on. Engineers label those two states 0 and 1, call each one a bit (short for binary digit), and build everything — numbers, letters, images, sound — out of long strings of them. Before you can do anything else in this course, you need to be completely comfortable moving between "the number as a human would write it" (decimal) and "the number as a circuit stores it" (binary, and its shorthand cousins octal and hexadecimal). That's the whole point of Week 1.

Analogy Think of a row of light switches nailed to a wall, each one labelled with a place value like a decimal digit is. A decimal number is a row of dimmer dials, each able to sit at 10 positions (0–9). A binary number is a row of ordinary light switches, each only able to be off or on (0 or 1). Both are just "position × value, added up" — binary is only different because each position can hold less information (2 choices instead of 10), so you need more positions to store the same number.

Positional number systems — the one formula that explains everything

Every number system you'll meet this week (decimal, binary, octal, hexadecimal) is a positional system: the value of a digit depends on where it sits, not just what symbol it is. You already know this instinctively — in 8973, the "8" is worth 8000, not 8, because of its position. The general formula for an n-digit number is:

N = an-1·rn-1 + an-2·rn-2 + … + a1·r1 + a0·r0

What it calculates: the value N of a number, built up from its digits and base. When to use it: any time you convert a number into or out of ANY base — every conversion trick below is really just a shortcut for evaluating or reverse-engineering this one formula. Condition: works for any radix r≥2, as long as you count digit positions from 0 at the rightmost digit.

Nthe value of the number in ordinary decimal terms — what you get when you "add it all up"
aithe digit (coefficient) sitting in position i. For decimal these are 0–9; for binary just 0–1; for octal 0–7; for hex 0–9 then A–F (=10–15)
rthe radix (base) — how many distinct digit symbols the system has. Decimal r=10, Binary r=2, Octal r=8, Hex r=16
nhow many digits the number has. Position 0 is always the rightmost (least significant) digit

Everything else this week — every conversion trick — is just a shortcut for evaluating or reverse-engineering this one formula. Two names to know: the leftmost digit is the MSB (Most Significant Bit — carries the biggest weight), the rightmost is the LSB (Least Significant Bit).

Converting binary → decimal

Just plug the bits straight into the formula with r = 2.

101002 = 1·24 + 0·23 + 1·22 + 0·21 + 0·20 = 16 + 4 = 2010

Memorising the powers of 2 (1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024…) makes this almost instant — you're just picking out which "slots" have a 1 in them and adding those slot-values.

Converting decimal → binary (repeated division by 2)

  1. Divide the decimal number by 2. Write down the remainder (0 or 1) — that's your next bit.
  2. Take the quotient and divide by 2 again. Write down that remainder.
  3. Keep going until the quotient hits 0.
  4. Read the remainders from bottom to top — that's your binary number, MSB first.

Analogy Repeated division is like repeatedly asking "how many groups of 2 fit, and what's left over?" — the same way you'd figure out how many pairs of socks (groups of 2) you can make from a pile, and whether one is left unpaired. Do that recursively on the leftover pile and you're peeling off one bit at a time, cleanest bit (LSB) first.

Binary ⇄ Octal and Binary ⇄ Hex — the free shortcut

Because 8 = 23 and 16 = 24, each octal digit is worth exactly 3 bits, and each hex digit is worth exactly 4 bits. So you never need to go through decimal — just chop the binary into groups of 3 (for octal) or 4 (for hex) starting from the LSB, and convert each group independently.

Octal011 110 0102 → group into 3s: 011=3, 110=6, 010=2 → 3628
Hex1110 0010 10002 → group into 4s: 1110=E, 0010=2, 1000=8 → E2816

This is the one genuine "trick" worth memorising this week — it's much faster than converting to decimal and back, and it's exactly why octal/hex exist at all: they're a compact, human-friendly way to write binary.

Tests: decimal → binary/octal/hex conversion

Convert 27 and 915 to unsigned binary, octal, hexadecimal.

Try it yourself first, then reveal the answer
Approach

Use the repeated-division method three times per number (÷2, ÷8, ÷16) — or convert to binary once, then use the 3-bit/4-bit grouping shortcut to get octal and hex for free. Q3
Tests: the radix/base concept — working the formula backwards

Find the base b that makes each equation correct: (a) 14/2=5, (b) 23×14=333, (c) 24+17=40.

Try it yourself first, then reveal the answer
Approach

Turn every number into its base-b expansion algebraically and solve for b. For (a): 14b=b+4, so (b+4)/2=5 → b=6. For (b): 23b=2b+3, 14b=b+4, 333b=3b²+3b+3. Expand (2b+3)(b+4)=2b²+11b+12, set equal to 3b²+3b+3, rearrange to b²−8b−9=0 → (b−9)(b+1)=0 → b=9 (reject the negative root). For (c): 24b=2b+4, 17b=b+7, 40b=4b → 2b+4+b+7=4b → b=11.

Answers: (a) 6, (b) 9, (c) 11.

Concept 2 of 3

Representing negative numbers with only 0s and 1s

Ordinary arithmetic has a "+" or "−" sign sitting outside the number. A digital circuit has no separate sign symbol — everything must be encoded purely as bits. There are three schemes on the slides; you only need to be fluent in the third.

1. Sign-magnitude

Reserve the MSB purely as a sign flag (0 = positive, 1 = negative); the rest of the bits store the plain magnitude. E.g. 01101 = +13, 11101 = −13. Problem: 00000 (+0) and 10000 (−0) are two different bit patterns for the same value zero — wasteful and awkward for circuits.

2. One's complement

To negate a number, flip every bit (0→1, 1→0 — this operation is called "complementing", and it's the same thing as a logic NOT, which you'll meet properly next week). E.g. 01101 (+13) → 10010 (−13). Still has the same two-zeros problem (00000 and 11111 both mean zero).

3. Two's complement — the one actually used everywhere

Take the one's complement (flip every bit), then add 1.

−X = NOT(X) + 1

What it calculates: the two's complement bit pattern for −X, from the bit pattern for +X. When to use it: whenever you need to negate a number, or subtract (since X−Y is done as X+(−Y), never as its own separate operation). Condition: start from the POSITIVE version's bits — flip every bit, then add 1.

E.g. +13 = 01101 → flip → 10010 → add 1 → 10011 = −13. Only one bit pattern represents zero, and — the big payoff — addition and subtraction can now be done with the exact same circuit as unsigned addition, with no special-case sign logic. This is why every real processor uses two's complement internally.

N = (−1)·an-1·2n-1 + an-2·2n-2 + … + a1·21 + a0·20

What it calculates: the decimal value of an n-bit two's complement bit pattern, directly from its bits. When to use it: converting a two's complement number back to decimal. Condition: only valid once you know the pattern IS two's complement — it's the same formula as unsigned binary, except the MSB carries a negative weight instead of a positive one.

an-1the MSB — in two's complement it carries a negative weight (−2n-1), unlike unsigned binary where every weight is positive. This single change is the entire mechanism that makes two's complement work.

Worked example: 11011 (5-bit two's complement) = (−1)·1·24 + 1·23 + 0·22 + 1·21 + 1·20 = −16 + 8 + 0 + 2 + 1 = −5. Quick rule of thumb: if the MSB is 1, the number is negative — no exceptions.

Analogy Think of a car odometer that only has 5 binary "dials". If you keep counting down past 00000, it doesn't go to a special "negative" display — it wraps around to 11111, then 11110, etc., exactly like a real odometer wrapping from 000000 to 999999 when you go one mile below zero. Two's complement is just decimal wrap-around arithmetic, but for binary — that's why the hardware doesn't need to treat negative numbers specially.

Value ranges and overflow

For an n-bit two's complement number, the range is −2n-1 to +2n-1 − 1 (asymmetric — one more negative number than positive, because 0 "uses up" one of the positive-side slots). E.g. for 5 bits: −16 to +15.

Overflow happens when the true mathematical result falls outside that range and so can't be represented correctly. Key exam fact: adding two numbers of different signs can never overflow (the true answer is always smaller in magnitude than the larger input); overflow can only happen when adding two numbers of the same sign and the result flips to the opposite sign.

+7 (0111) + +7 (0111) = 1110 → reads as −2. Same-sign inputs, sign flipped ⇒ overflow.

Binary / octal / hex arithmetic

Addition works exactly like decimal column-addition, except a carry is generated whenever a column's sum reaches the base (2 for binary, 8 for octal, 16 for hex) instead of 10. Subtraction is never built as its own circuit — instead, the hardware computes X − Y as X + (−Y), getting −Y via the two's complement trick above, so the same adder circuit handles both addition and subtraction. When adding two's complement numbers, any carry that pops out past the MSB is simply discarded.

Try it yourself first, then reveal the answer
Approach

Same column arithmetic you already know, except a carry happens the moment a column reaches 7 instead of 10 — e.g. 4+3=7, which in base 7 is "10" (write 0, carry 1). It's genuinely easier to sanity-check by converting to decimal first (6347=319, 2537=136), doing the sum in decimal, then converting the decimal answer back to base 7 with repeated division by 7.

Answers: Sum = 12207, difference = 3517, product = 2403257.

Practice — tests concept 2
Q5
Tests: two's complement value formula, and sign extension

Find the decimal value of: (a) 1010 (4-bit), (b) 111010 (6-bit), (c) FA16 (8-bit), (d) 3FA16 (10-bit) — all as two's complement numbers. What do you notice?

Try it yourself first, then reveal the answer
Approach

Apply N = −an-1·2n-1 + (rest of the bits normally) to each. (a) 1010: −8+0+2+0 = −6. (b) 111010: −32+16+8+0+2+0 = −6. (c) FA16 = 1111 1010: unsigned value 250, since MSB=1 subtract 256 → 250−256 = −6. (d) 3FA16 as a 10-bit number = 1111111010: unsigned value 1018, subtract 1024 → −6.

Answer: all four equal −6. Conclusion: this is sign extension — if you widen a two's-complement number by adding more bits to the left, you must fill those new bits with copies of the sign bit (all 1s here, since it's negative), not with zeros. Do that and the value never changes, no matter how many bits you add.

Practice — tests concept 2
Q6
Tests: 2's complement addition/subtraction and overflow detection

For 8-bit two's complement pairs (A,B), compute A+B, A−B, −A+B, −A−B and explain any unusual results.

Try it yourself first, then reveal the answer
Approach

Get −A and −B first (flip all bits, add 1), then every operation becomes a straight addition: A−B is really A+(−B), and −A−B is really (−A)+(−B). Add normally in binary and discard any carry out of the MSB. Whenever the two numbers being added share the same sign but the result comes out the opposite sign, that's overflow — the true answer didn't fit in 8 bits.

Answers: (a) 01010101+00001010 → +95, +75, −75, −95 (no overflow anywhere — signs of inputs to each sum always differ or the magnitude is safely in range). (b) 01101011+00101010: A+B overflows (two positives summing past +127), −A−B also overflows; A−B=+65, −A+B=−65. (c) 11101010+00101111 → +25, −69, +69, −25. (d) 10000000+01111111: −A+B is −128+127=−1 (fine), A+B overflows (opposite-signed inputs summed together with the negative one already at the extreme −128 boundary), and −A and −(+127) both hit the "can't be represented" edge case since +128 doesn't exist in 8-bit two's complement.

Discussion — detecting overflow: the reliable hardware rule is: compare the carry into the MSB position with the carry out of the MSB position. If they differ, overflow occurred. (The "same sign in, different sign out" rule above is the human-friendly version of the exact same test.)

Concept 3 of 3

Codes: BCD, Gray code, ASCII

BCD (Binary-Coded Decimal)

Instead of converting a whole decimal number into pure binary, BCD encodes each decimal digit separately as its own 4-bit binary value (0000–1001 only; 1010–1111 are illegal/unused). It's a compromise: easy for humans/displays to read back the original decimal digits, at the cost of wasting 6 of the 16 possible 4-bit patterns.

38610 → 0011 1000 0110 (3) (8) (6)

Gray code

Ordinary binary can change multiple bits at once between adjacent numbers (0011→0100 flips 3 bits). In real circuits, bits never switch at exactly the same instant, so during that transition the circuit can briefly show a completely wrong intermediate value — a real problem for things like rotary position sensors. Gray code is reordered so that only one bit changes between any two consecutive values.

Analogy Imagine a combination lock with several dials that must all click over at once when you go from 3 to 4 — if they don't click in perfect sync, the lock briefly shows nonsense combinations. Gray code is like redesigning the dial sequence so only ONE dial ever needs to move between consecutive numbers — nothing can ever be caught "mid-click" on more than one wheel at a time.

To build it: mirror the smaller Gray code sequence, prefix the original half with 0 and the mirrored half with 1. (See the reflect-and-prefix construction on slide 43 if you want the full mechanical procedure — worth re-deriving once by hand rather than memorising the table.)

ASCII

A 7-bit code (128 possible patterns) that assigns one bit-pattern to each letter, digit, and punctuation symbol, so text can be stored/transmitted as bits. E.g. "I" = 1001001, "E" = 1000101. You don't need to memorise the table — just understand it's a fixed lookup, same idea as BCD but for text instead of digits.

Practice — tests concept 3
Q8
Tests: BCD encoding

Encode 39, 625, 1950, 94704 in BCD. Is a BCD number binary or decimal?

Try it yourself first, then reveal the answer
Approach

Encode each decimal digit independently as 4 bits (0000–1001) and concatenate — never treat the whole number as one binary value.

Answers: 39 → 0011 1001. 625 → 0110 0010 0101. 1950 → 0001 1001 0101 0000. 94704 → 1001 0100 0111 0000 0100.

Discussion: Neither, exactly — it's both. Physically it's a string of bits (binary), but structurally/semantically it's decimal: each 4-bit nibble is a direct stand-in for one decimal digit, so the "shape" of the underlying number in decimal is fully preserved, unlike a true binary conversion.

Practice — tests concepts 1, 2 & 3
Q9
Tests: the same bit pattern read three different ways

A 12-bit register holds 100010010111. What decimal value does it represent as (a) 3 BCD digits, (b) unsigned binary, (c) 2's complement?

Try it yourself first, then reveal the answer
Approach

This question exists to hammer home that bits have no inherent meaning — the same 12 bits mean three completely different things depending on what encoding you decide to interpret them as. (a) Split into 4-bit nibbles: 1000 1001 0111 = 8, 9, 7 → 897. (b) Treat the whole 12 bits as one plain binary number: 2048+128+16+4+2+1 = 2199. (c) Same bits, but MSB=1 means negative: 2199 − 4096 = −1897.

Answers: (a) 897, (b) 2199, (c) −1897.

✍️ Write This Down

Copy these into your own notes (in your own words where you can):

  • The positional formula N = Σ ai·ri, and what each symbol (ai, r, n, N) means.
  • Decimal→any-base = repeated division, read remainders bottom-to-top. Any-base→decimal = plug into the formula directly.
  • Binary↔Octal groups bits in 3s; Binary↔Hex groups bits in 4s — memorise this, it's the fastest tool in the whole chapter.
  • Two's complement rule: to negate, flip all bits and add 1. Formula: N = −an-12n-1 + rest as normal.
  • n-bit two's complement range: −2n-1 to +2n-1−1 (one extra negative number, no extra positive one).
  • Overflow rule: only possible when adding two numbers of the same sign; detect it by comparing carry-in vs carry-out of the MSB.
  • Sign extension: widening a two's complement number means copying the sign bit into the new higher positions, not padding with 0.
  • BCD = each decimal digit gets its own 4-bit code (0000–1001); codes 1010–1111 are invalid/unused in BCD.
  • Gray code changes exactly one bit between consecutive values — used to avoid glitches from multiple bits switching at slightly different times.
  • The same bit pattern means different values depending on what encoding (unsigned / 2's complement / BCD / ASCII…) you choose to interpret it as. Bits alone carry no built-in meaning.

🟥 Redstone Build: Visualising Number Systems

You haven't met logic gates yet (that's next week), so this week's build is about seeing place value physically rather than building logic — a warm-up for the real circuits that start in Week 2.

Build: an 8-bit "place value" display wall

  1. Place a row of 8 redstone lamps in a line, each sitting one block above a length of redstone dust.
  2. Under each lamp, place a lever that toggles the dust beneath it on/off (on = lamp lit = bit value 1; off = bit value 0).
  3. Label each lever's position (with a sign, item frame, or just memorised order) with its place value from left to right: 128, 64, 32, 16, 8, 4, 2, 1 — mirroring 27 down to 20.
  4. Pick a decimal number (say 168), and physically flip the levers to represent it in binary (10101000), lighting up only the lamps whose place values sum to 168 (128+32+8=168). This is literally you performing the decimal→binary conversion with your hands.
  5. Reverse the exercise: flip a random combination of levers, read off which lamps are lit, and add up their labelled place values to get the decimal number — this is the binary→decimal formula, done physically.

Optional extension: build a second row of 8 lamps 3 blocks below, and re-group the top row's levers visually into groups of 4 with a small gap between groups. Label each group of 4 with its hex digit value (0–F) — this turns the same wall into a live hex/binary converter, since grouping bits in 4s is the hex-conversion shortcut from the slides.
